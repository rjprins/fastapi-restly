CRUD Routes#

AsyncRestView and RestView give one SQLAlchemy model five CRUD routes. A subclass sets the URL prefix and the model, and it can also set the schemas. include_view() registers the routes:

@fr.include_view(app)
class UserView(fr.AsyncRestView):
    prefix = "/users"
    model = User

UserView now serves requests to list, create, get, update and delete users under /users. Build a Blog API shows the app, the database configuration and the model around such a view, in one file that runs. include_view also works as a direct call; see Register a view.

Each route runs a fixed list of steps, such as loading the row, authorize and the commit. How a CRUD route runs explains these steps. Each route also has a page of its own: List, Get One, Create, Update and Delete. It shows the steps of that route in order, and a table of what you can change.

Choose async or sync#

Use AsyncRestView for a new application, unless the application already uses synchronous SQLAlchemy. It gets an AsyncSession through fr.AsyncSessionDep, and the methods you override are async def methods.

Use RestView with synchronous SQLAlchemy sessions, or with libraries that only work synchronously. It gets a Session through fr.SessionDep, and the methods you override are plain def methods.

Apart from this, the two classes are the same: the same routes, the same configuration and the same methods to override. You choose for each view, so one application can use both. Database & Configuration shows how to configure the sessions. To give one view another session, see Use another database on one view. The examples on this page use AsyncRestView.

The main path of the list is /users, without a slash at the end. Restly also accepts /users/, as a route that OpenAPI does not show.

GET /users takes the filter, sort and page parameters that Filtering, Sorting & Pagination defines, and it is paginated by default. Responses shows the response bodies and how to change the data envelope.

A row that does not exist returns 404, and so does a row that the view’s scope hides. Each write commits before Restly builds the response, and a read does not commit; see What commits, and when.

Important

Restly does not authenticate requests, and by default it allows every action on every route. Add authentication with FastAPI dependencies; see Run a dependency on every route. Then decide per action who may do what in authorize(); see Authorization.

Item paths and static routes#

The paths of the built-in GET, PATCH and DELETE routes for one row follow id_type. By default, Restly takes it from the model’s primary key. The PUT route of a React Admin view uses the same path.

ID type

Registered item path

Matching values

int

/{id:int}

Digits only, including 0; no minus sign

uuid.UUID

/{id:uuid}

UUIDs that Starlette’s converter accepts

Any other type

/{id}

Any single path segment, then FastAPI validation

With an integer or UUID item path, a static route such as /users/me still works when you register it after the view.

An untyped item path, such as the path for string ids, also matches /users/me. Register a static route like that before the item route.

Details

A value that does not match the converter returns 404, unless another route matches it. So a negative integer id does not match, even when the row exists. OpenAPI still shows the path as /users/{id}, with an integer or UUID parameter.

A route that you declare yourself keeps the path you give it. Restly adds the converter only to a path parameter annotated IDType; see Name the view’s schemas in a custom route. To accept negative integer ids, replace each item endpoint you need with an untyped path such as @fr.get("/{id}"), and annotate its id parameter as int; see Replace an endpoint method.

The item routes use the name id in the path. An existing API can use another name, such as {user_id}. The URLs are the same, but OpenAPI and the clients that are generated from it show the name. To keep that name, replace each item endpoint, and put on a React Admin view, with a path such as @fr.get("/{user_id:int}") and a parameter user_id: int. With the converter, a wrong value still answers 404, and /users/me still works after the view.

OpenAPI does not allow two paths that differ only in the names of their parameters. So /{id} next to /{user_id} on one view raises an error when you register the view. Use the same name in both paths.

How a CRUD route runs#

Take POST /, the create route. FastAPI calls create_endpoint, the endpoint method. It calls handle_create, the handler. The handler runs the steps, and calls create, the business method:

  • POST /
    • create_endpoint(data)overrideThe endpoint method: the HTTP contract.
      • handle_create(data)The handler: it runs the steps. It is final.
        • authorize("create", data=data)override
        • Check the references in the data. An id that does not exist is a 404.
        • create(data)overrideThe business method: it builds the object. Nothing is written yet.
        • Save: flush, refresh the object, and load it with the loader options.

          The save does what session.flush() and session.refresh() do in plain SQLAlchemy. It flushes the session. Then it refreshes the object, and every other row of the view’s model that the action wrote. It loads them with the view’s loader options, as a read does: the relationships that the response shows, and any value that you add there. So the hooks and the response see the saved rows. Rows of other models are written, but not refreshed.

        • before_action_commit("create", new=obj, old=None)override
        • Commit.
        • after_action_commit("create", new=obj, old=None)override
      • to_single_response(obj)overrideThe response of the object.

A method marked override is a method that you can override in your view. A step with an arrow opens and closes when you click it. The page of each route, such as Create, shows the steps of that route.

Every CRUD route has these three methods. The names follow one pattern for all five actions: update_endpoint calls handle_update, which calls update, and so on. A read has a load in the place of the business method.

  • The endpoint method, <verb>_endpoint, is the method that FastAPI calls. It owns the HTTP contract: the route decorator, the parameters and the response_model. It returns the row, and Restly builds the response with to_single_response. To change one option of the route, such as the status code, use fr.modify_route. Replace the method only when the change needs code. See Replace an endpoint method.

  • The handler, handle_<verb>, runs the steps. It calls authorize, checks the references in the data, and then calls the business method. On a write, it ends with the commit bracket: it saves the object, runs before_action_commit, commits, then runs after_action_commit. It returns the object. Only the delete handler returns nothing. A handler is final: a view class that defines one fails when Python creates the class. A custom route calls a handler to run the same steps.

  • The business method of a write is the bare verb: create, update or delete. It makes the change: it builds the object or applies the input to it, and returns it. It does not check permissions, does not flush and does not commit. So when your override runs, authorize and the reference checks have already passed. Nothing is written while it runs. The save after it writes the change, and then the commit follows.

  • A read has a load: get_one or get_many. A load is final, as a handler is. You change it through the scope, the list params, the loader options and two small hooks. See Visibility, then policy.

Details

Update and delete have the same steps, with a load first. Their handlers load the row through get_one, so a row that the caller cannot see is a 404. Then they call authorize with the loaded row, check the references in the data, and take a snapshot of it as old. The business method runs next, then the commit bracket. The delete business method only marks the row for deletion.

The row that an action is about is its subject: the object that create or update returns, or the row that delete gets. old is the subject before the action, and new is the subject after it. So the hooks can see what changed. After a delete, the row is gone and new is None. A soft delete keeps the row, so new is the row.

The business method runs under SQLAlchemy’s session.no_autoflush. So a query inside it does not write a half-built object, also on a RestView, whose session flushes before each query everywhere else.

The save writes every change in the session. It refreshes the object that the business method returns, and every other row of the view’s model that the action wrote. A row of another model that the method changes, such as a line of an order, is written but not refreshed. When the change set a foreign key column of such a row, such as line.product_id, the save unloads that relationship. So a response that nests the line loads the new product, not the old one. A business method that you call yourself, outside a handler or a write_action block, writes nothing: the handler does the save.

Set the model and the schemas#

A CRUD view sets two class attributes:

  • prefix: the URL prefix of every route of the view.

  • model: the SQLAlchemy mapped class that the routes read and write.

Normal models built on SQLAlchemy’s DeclarativeBase work. Restly’s model defaults, fr.ModelDefaults, are optional; see Models.

If the view does not declare schema, Restly generates the view’s main schema from model when you register the view. From the main schema, it derives the create, update and response schemas: create_schema, update_schema and response_schema. Generate the schema or write it shows when to write the schema yourself, and Hide a field from requests or from responses shows which fields each schema takes.

Change one option of a route#

To change one option of a route that a view inherits, use fr.modify_route under the name of the route method. The route keeps its method and its other options:

class InvoiceView(fr.AsyncRestView):
    prefix = "/invoices"
    model = Invoice
    schema = InvoiceSchema

    get_many_endpoint = fr.modify_route(
        summary="List invoices", operation_id="billing_list_invoices"
    )
    create_endpoint = fr.modify_route(status_code=200)
    update_endpoint = fr.modify_route(methods=["PUT"])

This changes the route of this view and its subclasses. The route of the base class stays the same.

It takes the same arguments as a route decorator. The hooks of the view run as before. Restly still fills in what you do not pass: the list params, the name, the summary and the operation ID. When you pass name, FastAPI makes the summary and the operation ID from that name, unless you pass them too. The table in The names and operation IDs of the CRUD routes lists the endpoint methods.

Details

Each argument replaces the one of the inherited route. dependencies and responses add up, as they do on a view. dependencies run base first, so a subclass cannot remove a check of its base. responses add up per status code, and a status code set to None is left out:

    delete_endpoint = fr.modify_route(dependencies=[Depends(require_admin)])
    get_one_endpoint = fr.modify_route(responses={404: None})

FastAPI adds the 422 response itself, so {422: None} does not remove it.

path replaces the path of the route, as in fr.modify_route("/new"). Restly also serves the list route and the create route at /invoices/, with a slash at the end, hidden from OpenAPI. To leave out these hidden routes, set path="" on the list route and on the create route. In a new path of an item route, write {id}. A path such as /{role_id} raises an error when the view registers: the method reads id, so nothing would read role_id.

methods=["PUT"] changes only the HTTP method. The route still updates only the fields that the client sends. A React Admin view already has a PUT route, put. So there, methods=["PUT"] on update_endpoint raises an error, because two routes would have the same path and HTTP method. A status code without a body, such as 204, also removes the response model of the route. For a delete with a body, write the method.

fr.modify_route changes how a route is served, not what it sends. So response_model and the other response_model_* arguments raise an error. A route of the view builds its response with to_single_response or to_list_response. Another response model would skip that step, and the fields that it hides would go out. To change the response of the view, set response_schema or list_response_schema. To send another schema from one route, write the method, for example a schema with more fields on GET /{id}:

    @fr.get("/{id}")
    async def get_one_endpoint(self, id: IDType) -> InvoiceDetailSchema:
        obj = await self.handle_get_one(id)
        return InvoiceDetailSchema.model_validate(obj)

Then the route decides what it sends, as a plain FastAPI route does.

An option does not change the order of the routes. So a route that the class writes, such as GET /stats, stays before the item route.

A subclass inherits the options and can change them further. A plain class can hold options for several views. Put it before the view class, as in class TagView(QuietRoutes, fr.AsyncRestView), as for any other method of a mixin. After the view class, the options would do nothing, so Restly raises an error when Python defines the class.

A name that is not a route of a base class raises RestlyConfigurationError when Python defines the class. Use fr.modify_route in the class body. An argument that FastAPI does not know raises a TypeError when the view registers, as it does on a route decorator.

A method with a route decorator states the whole route. So options from a base class do not apply to it. Write such a method when the change needs code, such as a decorator on the route or a response header. It can call the method of the base class, so the route works as before:

    @fr.post("/")
    async def create_endpoint(
        self, data: CreateSchema, response: Response
    ) -> ResponseSchema:
        obj = await super().create_endpoint(data)
        path = self.request.url.path.rstrip("/")
        response.headers["Location"] = f"{path}/{obj.id}"
        return obj

ResponseSchema keeps the view’s response as the response model; see Name the view’s schemas in a custom route. An item route that you declare, such as GET /{id}, keeps the path that you give it. Restly adds the int or uuid converter only to a path parameter annotated IDType; see Item paths and static routes.

Leave out a route#

To leave out a route that the view inherits, set its method to None:

@fr.include_view(app)
class UserView(fr.AsyncRestView):
    prefix = "/users"
    model = User
    update_endpoint = None
    delete_endpoint = None

UserView now serves only GET /users, POST /users and GET /users/{id}.

A subclass inherits the None. To make several views read-only, set it on a base view:

class ReadOnlyView(fr.AsyncRestView):
    create_endpoint = None
    update_endpoint = None
    delete_endpoint = None


@fr.include_view(app)
class ProductView(ReadOnlyView):
    prefix = "/products"
    model = Product

ProductView only serves GET /products and GET /products/{id}.

A subclass leaves out only the routes that it sets to None. So it also serves the custom routes of its base, such as POST /tags/merge, and also a write route that someone adds to the base later. For a read-only copy of a view with custom routes, put the shared settings in a base view, and subclass it twice. Then the copy does not inherit the custom routes of TagView:

class TagBase(fr.AsyncRestView):
    model = Tag


@fr.include_view(app)
class TagView(TagBase):
    prefix = "/tags"

    @fr.post("/merge")
    async def merge(self, source_id: int, target_id: int) -> None: ...


@fr.include_view(app)
class PublicTagView(TagBase):
    prefix = "/public/tags"
    create_endpoint = None
    update_endpoint = None
    delete_endpoint = None

PublicTagView serves only the two read routes, also when TagView gets more routes later. But both views serve a route that TagBase gets later.

Details

None works the same for a custom route, such as merge = None, and on a plain fr.View. Restly does not check the name, so a typo such as delte_endpoint = None leaves out nothing. fr.modify_route on a route that a base sets to None raises an error, because there is no route to change.

Change what a write does#

Each write has a business method: create, update or delete. Override only the one you need. The handler still checks permissions and commits around it. The page of each write shows its business method in full: Create, Update and Delete.

Before you set a value in create or update, ask which write paths must set it, as Set a value on every write path explains:

  • A value that every write path must set belongs on the model, as a column default or a mapper event.

  • A value that only the HTTP routes set belongs in create or update.

The common cases:

  • Hash a password: in create. The plain password arrives in the request body, and only the route has it. A script that also gets plain passwords calls the same function: see Run the same logic in a script or a worker.

  • Make a slug from the title: on the model. Every new row needs a slug, whichever path writes it.

  • Keep a total on a parent row up to date, such as the story points of a project: on the model. The total is wrong as soon as one write path skips it.

  • Send an event about a change: in a commit hook, for an event about an action of the view. An event that every write path must send needs a SQLAlchemy session event instead.

Replace an endpoint method#

Business methods and hooks keep the HTTP side of a route: its path, its parameters and its response. To change only an option of the route, such as its status code, use fr.modify_route; see Change one option of a route. Replace the endpoint method when the change needs code: the headers, the parameters or what the route returns.

Define a method with the same name, such as delete_endpoint, and give it a route decorator. Keep the call to the handler, so the steps of the route still run. The page of each route has an example: List, Get One, Create, Update and Delete. To change the shape of the response body, such as an envelope around one object, see Change the shape of one route.

When several views need the same replacement, put it in a mixin. List the mixin before the view class, so Python finds its method first:

from fastapi_restly.views import IDType, ResponseSchema


class DeleteReturnsObjectMixin:
    @fr.delete("/{id}", status_code=200)
    async def delete_endpoint(self, id: IDType) -> ResponseSchema:
        obj = await self.get_one(id)
        response = self.to_single_response(obj)
        await self.handle_delete(id)
        return response


@fr.include_view(app)
class ProductView(DeleteReturnsObjectMixin, fr.AsyncRestView):
    prefix = "/products"
    model = Product

IDType and ResponseSchema give each view that uses the mixin its own id type and response schema. The React Admin views use this pattern. They replace get_many_endpoint for the ra-data-simple-rest contract, and keep the handlers, the loads and the business methods.

Details

When Restly registers the view, an endpoint method that the class defines replaces the inherited method with the same name. The other inherited endpoint methods stay. A method with no route decorator is not a route, so the view then has no such route. With fr.configure(warn_on_misuse=True), Restly warns about it.

The built-in endpoint methods get the view’s types from markers, such as get_one_endpoint(self, id: IDType) -> ResponseSchema. A replacement gets the view’s types only where it uses the markers too; see Name the view’s schemas in a custom route. A parameter or a return without an annotation gets no type. Restly keeps an annotation that you write, so data: ProductReplace validates the request body against ProductReplace. list_params is the exception: it always gets the view’s list_params_schema.

What the default routes do not do#

The default CRUD routes have these limits:

  • A row is identified by one primary key column. The {id} path parameter takes the Python type of the key, so a UUID or string key needs no configuration. Reference fields such as fr.MustExist[UUID, Model] accept these keys too. For a composite key, set id_type = str and override where_id to read the parts of the key from the path; see Find the row by another key. Without where_id, a view of such a model fails when it registers, unless it leaves out the item routes.

  • Responses can contain nested objects, and lists can filter on relationships. Request bodies with nested objects are not supported in general. Use MustExist, IDRef or IDSchema to refer to other rows, or change the payload in a business method; see Relationships.

  • The update route uses PATCH, not PUT. Add a PUT route only when the client needs one; see Replace update_endpoint.
