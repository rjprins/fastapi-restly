Request Lifecycle & Hooks#

Every CRUD route of a RestView or AsyncRestView runs the same steps in the same order. It checks that the caller may act, makes the change, commits it and builds the response. Each step is a method on the view. To change a route, you override the method of one step. A custom route calls the same methods, so it runs the same steps.

CRUD Routes lists the default routes and their settings. Views covers what every view shares: registration, dependencies and inheritance.

How a view handles a request#

Take POST /, the create route. FastAPI calls create_endpoint, the endpoint method. It calls handle_create, the handler. The handler runs the steps in this order:

POST /
  └─ create_endpoint(schema_obj)                 # endpoint method: the HTTP contract
       ├─ handle_create(schema_obj)              # handler: runs the steps (final)
       │    ├─ authorize("create", data=schema_obj)
       │    ├─ create(schema_obj)                 # business method: the change
       │    │    ├─ make_new_object(schema_obj)   # build the ORM object (final)
       │    │    └─ save_object(obj)              # flush and refresh, no commit (final)
       │    ├─ before_action_commit("create", new=obj)
       │    ├─ commit
       │    └─ after_action_commit("create", new=obj)
       └─ to_response(obj)

Every CRUD route has these three methods. The names follow one pattern for all five actions: update_endpoint calls handle_update, which calls update, and so on.

  • The endpoint method, <verb>_endpoint, is the method that FastAPI calls. It owns the HTTP contract: the route decorator, the parameters, the response_model and the call to to_response. Replace it only to change that contract, such as the status code. See Change the status code, headers or response of one route.

  • The handler, handle_<verb>, runs the steps. It calls authorize and then the business method. On a write, it ends with the commit bracket: before_action_commit, the commit, then after_action_commit. It returns the object. Only the delete handler returns nothing. A handler is final: a view class that defines one fails when Python creates the class. A custom route calls a handler to run the same steps.

  • The business method is the bare verb: create, update, delete, get_one or get_many. It makes the change: it builds the object, applies the input and saves. It does not check permissions and does not commit. So when your override runs, authorize has already passed, and the commit comes after it.

Update and delete have the same steps, with a load first. Their handlers load the row through get_one, so a row that the caller cannot see is a 404. Then they call authorize with the loaded row and take a snapshot of it as old. The business method runs next, then the commit bracket. The hooks receive both new and old, so they can see what changed.

A read: visibility, then policy#

A read has no commit bracket. Two steps decide whether the caller gets the row:

GET /{id}
  └─ get_one_endpoint(id)            # endpoint method
       ├─ handle_get_one(id)         # handler
       │    ├─ get_one(id)           # business method
       │    │    └─ the view scope   # VISIBILITY: soft delete, role, row-level
       │    │                        #   a hidden row is a 404 for every caller
       │    └─ authorize("get_one", obj=obj)   # POLICY: checks the loaded row
       └─ to_response(obj)

  • Visibility. The business method get_one loads the row through the view’s scope. A row outside the scope is a 404 for every caller, as if the row did not exist. See Scopes.

  • Policy. The handler then calls authorize("get_one", obj=obj) with the loaded row. A refusal is a 403. See Authorization.

get_one itself does not call authorize: the handler does. A list has the same two steps in the other order. handle_get_many first calls authorize("get_many"), with no row. Then get_many applies the scope and the client’s filters, sort and page (apply_list_params). On a paginated view, it also counts the total (count).

Start at the business method. Move a side effect that depends on the commit to a hook. Replace the endpoint method only when the HTTP contract changes.

Change what an action does#

Override the business method of the action: create, update, delete, get_one or get_many. Override only the one you need. The handler still checks permissions and commits around it.

Before you set a value in create or update, ask which write paths must set it. The view’s routes are not the only code that writes rows. Scripts, jobs, imports and the fr.objects functions write them too, and they never call the view.

  • A value that every write path must set belongs on the model, as a column default or a mapper event. Models shows both.

  • A value that only the HTTP routes set belongs in create or update.

The common cases:

  • Hash a password: in create. The plain password arrives in the request body, and only the route has it. A script that also gets plain passwords calls the same function: see Run the same logic in a script or a worker.

  • Make a slug from the title: on the model. Every new row needs a slug, whichever path writes it.

  • Keep a total on a parent row up to date, such as the story points of a project: on the model. The total is wrong as soon as one write path skips it.

  • Send an event about a change: in a transaction hook, for an event about an action of the view. An event that every write path must send needs a SQLAlchemy session event instead.

Hash a password in create#

import fastapi_restly as fr
from sqlalchemy.orm import Mapped

from .auth import hash_password
from .models import Base


class User(fr.IDMixin, Base):
    email: Mapped[str]
    password: Mapped[str]  # stores the hash. UserView.create writes it


class UserSchema(fr.IDSchema):
    email: str
    password: fr.WriteOnly[str]  # accepted on input, never in a response


@fr.include_view(app)
class UserView(fr.AsyncRestView):
    prefix = "/users"
    model = User
    schema = UserSchema

    async def create(self, schema_obj):
        obj = await self.make_new_object(schema_obj)
        obj.password = hash_password(schema_obj.password)
        return await self.save_object(obj)

handle_create still calls authorize and commits. The override only changes how the object is built. The schema field and the column have the same name, because make_new_object passes every writable schema field to the model’s constructor. So the plain password goes into password first, and the override replaces it with the hash before the flush. fr.WriteOnly keeps the field out of every response.

The generated update body takes password too. Without more code, PATCH /users/{id} stores a new password as plain text. So hash it in update as well:

    async def update(self, obj, schema_obj):
        obj = await self.update_object(obj, schema_obj)
        if "password" in schema_obj.model_fields_set:
            obj.password = hash_password(schema_obj.password)
        return await self.save_object(obj)

update_object writes only the fields that the request sends, so the check uses the same set. The other way is an explicit update schema without password, with a separate route that changes the password.

Refuse a change in update#

update receives the row that handle_update has already loaded through the scope, not the id. A rule that needs the stored row or the database goes here:

    async def update(self, obj, schema_obj):
        if obj.locked:
            raise fr.exc.Conflict("This record is locked")
        obj = await self.update_object(obj, schema_obj)
        return await self.save_object(obj)

A rule about who may make the change goes in authorize. A rule about one field’s value is a Pydantic validator on the schema: see Validation. Errors lists the exceptions to raise.

Add a value to each row of a list#

To change the rows after the query, override get_many and call super():

    async def get_many(self, list_params, *, scope=None):
        result = await super().get_many(list_params, scope=scope)
        for project in result.objects:
            project.can_edit = project.owner_id == Current.user_id()
        return result

Current.user_id() is the id of the caller (Current & ContextParam). The view’s schema declares the field:

    can_edit: fr.ReadOnly[bool | None] = None

It is not a column, so ReadOnly keeps it out of the create and update bodies. The handlers always pass scope=, so the override declares it and passes it on. To change the single-row read too, override get_one the same way, as the SaaS example does.

Other changes to a list have their own place. A scope hides rows. apply_list_params changes the filter, sort and page grammar (Filtering & Pagination). get_relationship_loader_options loads more relationships (Relationships).

Build and save objects#

The business methods are built from three utilities. Call them from your create and update overrides. They are final: a view class that defines one, itself or through a mixin, fails when Python creates the class.

Method

What it does

self.make_new_object(schema_obj)

Builds a new ORM object from the schema and adds it to the session. It resolves references and skips the fields that the schema marks read-only. It does not flush.

self.update_object(obj, schema_obj)

Writes the writable fields that the client sent onto an existing object, and resolves references. It does not flush.

self.save_object(obj)

Flushes and refreshes obj, then loads the relationships that the response class names. It does not commit.

None of them commits. The handler, or a write_action block, commits.

The same operations are functions in fr.objects, for code outside a view: async_make_new_object, async_update_object, async_save_object and async_delete_object, and their sync versions. See The same operations outside a view. These functions do not call authorize or the hooks. They only build, change, save or delete.

Run the same logic in a script or a worker#

While the view is the only caller, keep the logic in its create or update. There it has self.session, self.request and the view’s dependencies.

When a script or a worker must run the same logic, move it into a plain function and call it from both:

from fastapi_restly.objects import async_make_new_object, async_save_object


def set_password(user: User, raw_password: str) -> None:
    user.password = hash_password(raw_password)


class UserView(fr.AsyncRestView):
    prefix = "/users"
    model = User
    schema = UserSchema

    async def create(self, schema_obj):
        user = await self.make_new_object(schema_obj)
        set_password(user, schema_obj.password)
        return await self.save_object(user)


async def import_user(session, payload) -> User:
    user = await async_make_new_object(session, User, payload)
    set_password(user, payload.password)
    await async_save_object(session, user)
    await session.commit()
    return user

The script owns its transaction, so it commits itself. Do not move logic out of the view before there is a second caller.

A value that every write path must set does not need this. Put it on the model (Models), and every path gets it.

What commits, and when#

Restly commits for you, once for each write action. The handler of a write route, or a write_action block in a custom route, runs before_action_commit, commits, and then runs after_action_commit. Your business methods and hooks do not commit.

The session that Restly opens for a request does not commit when the request ends. It rolls back and closes. So a custom route that writes must commit through a handler or a write_action block. When a request ends with changes that are not committed, Restly warns with RestlyUncommittedChangesWarning. The warning is on by default. To turn it off for the app, pass warn_on_uncommitted=False to fr.configure. A route that rolls back on purpose, such as a dry run, can turn it off for one request with session.info["_fr_suppress_uncommitted"] = True.

A session generator of your own decides how a session is made and closed. It does not change who commits.

To commit several writes at once, see Commit several writes together.

Run code before or after the commit#

Every write action calls two hooks around its commit:

  • before_action_commit(action, new, old=None) runs inside the transaction, before the commit. What it writes is committed together with the change, or not at all. Use it for outbox rows and audit rows.

  • after_action_commit(action, new, old=None) runs after the commit, when the change is saved. Use it for email, webhooks and cache invalidation.

The hooks run for the CRUD writes and for every write_action block. Reads do not call them, and neither do the fr.objects functions. The arguments are:

  • action: the name of the action, such as "create", or the name that a custom route gives write_action. See Action names.

  • new: the saved object. On a delete, it is None.

  • old: a dict of the row’s column values before the change, from snapshot. It holds only the columns that were loaded. On a create, it is None.

With old, a hook can check what changed:

    async def after_action_commit(self, action, new, old=None):
        if action == "update" and old["status"] != new.status:
            await notify_status_change(new.id, new.status)

Do not change new or the database in after_action_commit. The commit is done, so the change is not saved. A change to new still shows in the response of this request, which hides the problem. Make the change in the business method or in before_action_commit.

On a delete, new is None and old holds the columns of the removed row. A delete that must finish outside the request can mark the row in delete, as a soft delete does. After the commit, after_action_commit starts the real delete:

    async def delete(self, obj):
        obj.status = "pending_deletion"
        await self.session.flush()  # no super(): the row stays

    async def after_action_commit(self, action, new, old=None):
        if action == "delete":
            await enqueue_async_delete(old["id"])  # a worker deletes the row

When after_action_commit raises#

The write is already committed, so an exception from the hook cannot undo it. The request still fails, and a client that tries again repeats the write. For an effect that may fail without harm, catch and log the error in the hook:

    async def after_action_commit(self, action, new, old=None):
        if action == "create":
            try:
                await send_confirmation_email(new.id)
            except Exception:  # the order is saved; don't fail the request
                logger.exception("Confirmation email failed for order %s", new.id)

An effect that must happen belongs in an outbox row, written in before_action_commit. A worker then delivers it and tries again when it fails. Make the delivery safe to repeat, because a retry can deliver it twice. FastAPI’s BackgroundTasks does not replace an outbox: a crash loses the task, and nothing tries it again.

Change the status code or headers of one route#

Business methods and hooks keep the HTTP contract of the CRUD route. Replace the endpoint method when the contract itself must change: the status code, the headers or the parameters. To change the shape of the response body, such as an envelope around one object, see Change the shape of one route on Responses. It replaces the endpoint method in the same way.

Define a method with the same name, such as delete_endpoint, and give it a route decorator. Most replacements call the handler and only change the response:

@fr.include_view(app)
class ProductView(fr.AsyncRestView):
    prefix = "/products"
    model = Product
    schema = ProductSchema

    @fr.delete("/{id}", status_code=200)
    async def delete_endpoint(self, id: int):
        obj = await self.get_one(id)               # load through the scope, or 404
        serialized = self.to_single_response(obj).model_dump(mode="json")
        await self.handle_delete(id)               # authorize, delete, commit
        return serialized

The default DELETE /{id} answers 204 No Content. This version answers 200 with the deleted row, as React Admin’s ra-data-simple-rest expects (React Admin).

When Restly registers the view, an endpoint method that the class defines replaces the inherited method with the same name. The other inherited endpoint methods stay.

Registration also fills in the view’s types where your method has no annotation, or Any. id gets id_type, schema_obj gets schema_create or schema_update, and the return annotation gets the route’s default response model. Restly keeps an annotation that you write, so schema_obj: ProductReplace validates the request body against ProductReplace. list_params is the exception: it always gets the view’s schema_list_params.

Change the list route#

Replace get_many_endpoint when the contract of the list changes, for example to send the total in a header. Keep the list_params parameter to keep Restly’s filter, sort and page parameters:

import fastapi
import json

ProductResponse = fr.schemas.derive_schema_response(ProductSchema)


@fr.include_view(app)
class ProductView(fr.AsyncRestView):
    prefix = "/products"
    model = Product
    schema = ProductSchema

    @fr.get("/", response_model=list[ProductResponse])
    async def get_many_endpoint(self, list_params):
        result = await self.handle_get_many(list_params)
        serialized = [
            self.to_single_response(obj).model_dump(mode="json")
            for obj in result.objects
        ]
        return fastapi.Response(
            content=json.dumps(serialized),
            media_type="application/json",
            headers={"X-Total-Count": str(result.total_count)},
        )

The route sends a plain list, not the default envelope, so it names its response_model. Without it, registration documents the envelope in OpenAPI, and generated clients expect the wrong body. Name the view’s classes in a custom route explains derive_schema_response.

Share a changed route across views#

When several views need the same contract, put the replacement in a mixin. List the mixin before the view class, so Python finds its method first:

class DeleteReturnsObjectMixin:
    @fr.delete("/{id}", status_code=200)
    async def delete_endpoint(self, id):
        obj = await self.get_one(id)
        serialized = self.to_single_response(obj).model_dump(mode="json")
        await self.handle_delete(id)
        return serialized


@fr.include_view(app)
class ProductView(DeleteReturnsObjectMixin, fr.AsyncRestView):
    prefix = "/products"
    model = Product
    schema = ProductSchema

The React Admin views use this pattern. They replace get_many_endpoint for the ra-data-simple-rest contract, and keep the handlers and business methods.

Add a custom read route#

A CRUD view can have more routes beside its CRUD routes. Declare a method with @fr.get, as on any view (Views). To load one row, call handle_get_one. It loads the row through the scope, so a row that the caller cannot see is a 404. Then it calls authorize("get_one", obj=row), as GET /{id} does. get_one alone also loads through the scope, but it does not call authorize.

The SaaS example’s GET /users/me returns the caller’s own row:

    @fr.get("/me", response_model=UserResponse)
    async def get_current_user(self) -> Any:
        """Get current user's profile."""
        user = await self.handle_get_one(Current.user_id())
        return self.to_single_response(user)

Current.user_id() is the id of the caller (Current & ContextParam). UserResponse is the view’s response class, so OpenAPI shows the same type as for GET /users/{id}. See Name the view’s classes in a custom route. The route /me works beside /{id}, because the item routes match only an integer id (Item paths and static routes).

The handlers return the ORM object, so a route can read every attribute of the model, also the ones that the response leaves out. In the same example, GET /projects/{id}/stats calls handle_get_one(id), and then counts the project’s tasks.

Look a row up by another key#

handle_get_one and get_one take a SQLAlchemy boolean expression in place of the id. The expression picks the row instead of the primary key. Everything else about the load stays the same: the view’s scope, the relationships that the response loads, and the 404.

    @fr.get("/by-email/{email}", response_model=UserResponse)
    async def get_by_email(self, email: str):
        user = await self.handle_get_one(User.email == email)
        return self.to_response(user)

Combine columns with sqlalchemy.and_(...). This is also how a custom route reaches a row of a model with a composite primary key. A plain id cannot name such a row, and passing one raises NotImplementedError.

The expression narrows the read inside the scope. It never reaches past it, so a row that the view hides stays a 404 under any key. Only scope changes what the view sees. When more than one row matches, Restly raises SQLAlchemy’s MultipleResultsFound and does not return the first row: a key that matches several rows is a bug in the expression.

handle_update and handle_delete take the same expression. So a custom PATCH /users/by-email/{email} route that calls handle_update(User.email == email, schema_obj) runs the same steps as PATCH /users/{id}. The SaaS example reads and updates projects by slug in app/projects/views.py.

Add a custom action route#

An action changes state: publish, archive, recalculate. Declare it with @fr.post, or with @fr.patch or @fr.delete. Most actions take one of three forms.

Change one row in a write_action block. Load the row with get_one. Then change it inside write_action, under the name of the action. The blog example publishes a post:

    @fr.post("/{id}/publish", status_code=200)
    async def publish(self, id: int):
        post = await self.get_one(id)
        async with self.write_action("publish", obj=post):
            if post.published:
                raise fr.exc.Conflict("Already published")
            post.published = True
        return self.to_response(post)

When the block starts, Restly calls authorize("publish", obj=post) and takes the snapshot of the row. When the block ends, Restly runs before_action_commit, commits, and runs after_action_commit, each with the action name "publish". If the block raises, as it does here for a post that is already published, nothing is committed. The route loads with get_one, not with handle_get_one, because write_action authorizes the action itself. Authorize a custom action shows how authorize handles a new name.

The SaaS example uses this form for the task changes POST /tasks/{id}/start, complete and reopen (app/tasks/views.py), and for POST /users/{id}/change-password (app/users/views.py).

Run a CRUD action under another path. When the action is a create or an update with another path or another body, call the handler, handle_create or handle_update. The route then runs every step of that CRUD action, with authorize and the commit. The SaaS example’s PATCH /users/me updates the caller’s own row:

    @fr.patch("/me", response_model=UserResponse)
    async def update_current_user(self, request: UpdateMeRequest) -> Any:
        user = await self.handle_update(Current.user_id(), request)
        return self.to_single_response(user)

UpdateMeRequest has only name and email, so this route cannot change other fields. update_object writes the fields of the schema it receives, and only the fields that the client sent. A change to the update business method applies here too.

Create in a block of your own. Some creates need more than create does, such as a parent row and its child rows. Use a write_action block without obj, and set the new object on the handle before the block ends:

    async with self.write_action("create", data=schema_obj) as w:
        obj = await self.make_new_object(schema_obj)
        w.obj = await self.save_object(obj)
    return self.to_response(w.obj)

The hooks receive w.obj as new. If the block ends without it, Restly raises RuntimeError. For a write that has no single object, pass obj=None instead. The SaaS example’s POST /uploads saves an upload and its lines this way (app/uploads/views.py). POST /task-labels/create-and-attach saves a label and its link to a task in one block (app/labels/views.py).

Name the view’s response classes in response_model, so OpenAPI shows the same types as for the CRUD routes: see Name the view’s classes in a custom route. A route that builds a schema with model_construct() skips validation, so its reference fields need the right form: see Build references in a custom route.

Commit several writes together#

Each handler and each write_action block commits on its own. To commit several of them at once, put them inside a shared_write_action_commit() block. The outermost block commits once. Then the queued after_action_commit hooks run:

    @fr.post("/bulk", status_code=201)
    async def bulk_create(self, items: list[OrderCreate]):
        async with self.shared_write_action_commit():
            orders = [await self.handle_create(item) for item in items]
        return [self.to_response(order) for order in orders]

Inside the block, each action still calls authorize, takes the snapshot, makes its change and runs before_action_commit. Then it flushes and returns. Its changes are not committed yet, and its after_action_commit has not run. So build the responses after the block, as in the example. Do the same for code that needs an after-hook to have run. On fr.RestView, use with and the sync handlers. The method has the same name.

The block can also hold other writes, for an operation on more than one model:

    async with self.shared_write_action_commit():
        project = await self.handle_create(project_data)
        self.session.add_all(
            Task(project_id=project.id, title=task.title)
            for task in source_tasks
        )
    return self.to_response(project)

The new project, the rows that its before_action_commit writes, and the copied tasks are committed together. If any part fails, none of them is committed.

Blocks inside each other share the commit when their views share a session. An exception that leaves a block cancels the shared commit and drops the queued hooks. This also happens when an outer block catches the exception. Rolling back stays the job of the session’s owner. A direct session.commit() inside the block raises RuntimeError, because the outermost block owns the commit.

When some rows may fail and the others must still be saved, put SQLAlchemy’s session.begin_nested() around each handler call. Catch the error outside that savepoint:

    from sqlalchemy.exc import IntegrityError

    async with self.shared_write_action_commit():
        for item in items:
            try:
                async with self.session.begin_nested():
                    await self.handle_create(item)
            except IntegrityError:
                continue

The savepoint holds the row’s change and the rows that its before_action_commit wrote. So a failed row rolls back both, and its queued after-hook is dropped. After the shared commit, the after-hooks of the saved rows run in order. They stop at the first exception.

The SaaS example runs both forms. POST /tasks/bulk, /tasks/bulk-delete and /tasks/import-csv put a savepoint around each row inside one shared_write_action_commit() block (app/tasks/views.py). POST /projects/{id}/clone commits a project, its outbox event and the copied tasks together (app/projects/views.py).

Internals#

The CRUD handlers and write_action share one implementation of the commit bracket: async_run_write_action and run_write_action. Each one calls authorize, takes the snapshot, runs a function that makes the change, and then runs before_action_commit, the commit and after_action_commit. Inside a shared_write_action_commit() block, it flushes instead of committing and queues the after-hook for the outermost block.
