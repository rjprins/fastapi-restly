Schemas & Validation#

Note

Restly says schema for a Pydantic class and model for a SQLAlchemy class. A User model is the database table. UserSchema, the view’s schema, is the public API.

A view has one schema, the view’s schema. It is a Pydantic class that lists the fields of the resource. When you register the view, Restly builds the classes of the routes from it:

Class

Used for

What Restly leaves out of the view’s schema

response class, UserResponse

everything that goes out

the WriteOnly fields

create body, UserCreate

the body of POST

the ReadOnly fields

update body, UserUpdate

the body of PATCH

the ReadOnly fields; every other field is optional

Each of these classes is a subclass of the view’s schema. So each one keeps the field types, the aliases and the validators of the view’s schema. Two markers decide which class keeps a field: fr.ReadOnly keeps it out of the request bodies, and fr.WriteOnly keeps it out of the responses. The filters and sort keys of the list route come from the response class too; Filtering & Pagination covers them.

You can set each class on the view yourself, as schema_response, schema_create or schema_update. Restly then uses your class as you wrote it. A view without a schema gets one that Restly generates from the model.

Generate the schema or write it#

Without a schema, Restly generates the view’s schema from the model. This is enough when the table is already the API you want:

@fr.include_view(app)
class UserView(fr.AsyncRestView):
    prefix = "/users"
    model = User

The generated schema has one field for each column, and no relationships. Restly marks id, created_at and updated_at as ReadOnly; see How Restly generates a schema for the details.

Write the schema yourself when the API differs from the table: other field names, fields that only go one way, references to other rows, or rules for the values. Set it on the view:

class UserSchema(fr.IDSchema):
    name: str
    email: str


@fr.include_view(app)
class UserView(fr.AsyncRestView):
    prefix = "/users"
    model = User
    schema = UserSchema

Restly writes each field of a request body to the model attribute with the same Python name. So name a field after its column, and use an alias when the JSON needs another name.

Choose a base class#

Restly has three base classes for a schema:

  • fr.IDSchema adds a read-only id field, as id: fr.ReadOnly[Any]. Most schemas use it. The id is in the responses, and the create and update bodies leave it out.

  • fr.BaseSchema is the class under IDSchema, without the id. Use it to declare every field yourself, id included. Mark the id ReadOnly if clients must not send it.

  • fr.TimestampsSchemaMixin adds read-only created_at and updated_at fields. Put it before the base class.

class UserSchema(fr.TimestampsSchemaMixin, fr.IDSchema):
    name: str
    email: str

BaseSchema is a Pydantic BaseModel with from_attributes=True, so it can read the attributes of an ORM object. It also checks that the markers are used in the right place; see the next section.

A request body that you set on the view, such as schema_create, can also be a plain pydantic.BaseModel. Its fields can still use ReadOnly, WriteOnly and fr.MustExist.

fr.IDSchema[User], with the model as a type parameter, gives the schema the model’s type; Type Annotations explains when that helps. As the type of a field, fr.IDSchema[User] is a reference to another row; see Relationships.

Hide a field from requests or from responses#

fr.ReadOnly[T] marks a field that only goes out. The create and update bodies leave it out, so a client cannot set it. A value that a client sends for it is ignored:

class UserSchema(fr.IDSchema):
    name: str
    created_by_id: fr.ReadOnly[int]

The server sets such a value. Set it on the model, with a column default, so that every write path sets it; see Stamp the fields the server owns.

fr.WriteOnly[T] marks a field that only comes in. The create and update bodies accept it, and no response shows it:

class UserSchema(fr.IDSchema):
    email: str
    password: fr.WriteOnly[str]

The two markers work in different places. This matters when you use a schema outside a view:

  • WriteOnly sets Pydantic’s exclude on the field. So every serialization of the schema drops it: the CRUD responses, a FastAPI response_model, and your own model_dump() calls. This also holds in nested schemas, and the response schema in OpenAPI does not show the field.

  • ReadOnly works only where Restly applies it: in the create and update bodies that Restly generates, and when Restly’s object helpers build or update an ORM object. On a schema that you use yourself, a ReadOnly field validates and serializes like any other field. OpenAPI marks it readOnly.

A marker must be the outer type of the field. Inside a union or a container, as in Optional[WriteOnly[str]], WriteOnly[str] | None or list[WriteOnly[str]], the marker would do nothing. So Restly rejects such a field with a RestlyConfigurationError. For an optional write-only field, write WriteOnly[Optional[str]].

A JSON column has its own rules for WriteOnly fields; see Validate the document in a JSON column.

Write the request body yourself#

A schema_create or schema_update that you set on the view is the whole contract for its request. Restly writes every field that it declares, except the fields that the class itself marks ReadOnly. The markers on the view’s schema only shape the bodies that Restly generates.

So you can set a field on create and freeze it afterwards. Mark it ReadOnly on the view’s schema, and declare it in your own create body:

class CommentSchema(fr.IDSchema):
    body: str
    story_id: fr.ReadOnly[int]


class CommentCreate(fr.BaseSchema):
    body: str
    story_id: fr.MustExist[int, Story]


class CommentView(fr.AsyncRestView):
    prefix = "/comments"
    model = Comment
    schema = CommentSchema
    schema_create = CommentCreate

POST /comments sets story_id. The generated update body leaves it out, so PATCH ignores it.

Keep a field that the server stamps, such as a tenant id, out of every request body that you write. Otherwise a client can set it.

Validate input#

Each kind of rule has one place:

Rule

Where it goes

What the client gets

The format or the range of one value

A Pydantic validator or a Field constraint on the schema

422

A field that a client cannot set

ReadOnly, or your own request body

The value is ignored

A referenced row must exist

fr.MustExist or a reference field; see Relationships

404

A value must be unique

A unique constraint on the column; see Errors

409

A rule that needs the database, the stored row or the caller

The create or update business method; see Request Lifecycle & Hooks

The error that you raise

Whether the caller may run the action at all is not validation. It is a policy, and it goes in authorize, which answers with 403.

Check the shape of a value#

Put a validator or a Field constraint on the view’s schema. The create body, the update body and the response class are subclasses of the view’s schema, so all three run it:

import re

import pydantic


class OrganizationSchema(fr.IDSchema):
    name: str = pydantic.Field(min_length=2)
    slug: str

    @pydantic.field_validator("slug")
    @classmethod
    def check_slug(cls, value: str | None) -> str | None:
        if value is not None and not re.fullmatch(r"[a-z0-9]+(-[a-z0-9]+)*", value):
            raise ValueError("use lowercase letters, digits and hyphens")
        return value

A value that fails returns 422, with Pydantic’s list of errors. The validator also runs in these places:

  • In the update body, every field is optional and accepts null. So a validator there can get None. Check for it, as above. Without the check, {"slug": null} breaks the validator, and the client gets a 500 instead of a 422. A null for a column that must have a value reaches the database, which rejects it with a 409.

  • The response class runs the validator when Restly builds a response from a row. A row that breaks the rule, for example one that a script wrote, then fails with a server error.

  • List filters run it on each filter value; see Filter values go through the field’s validation.

To check only what comes in, put the validator on a request body that you set on the view. The SaaS example does this for organizations (app/organizations/schemas.py).

A rule that compares two fields, in a model_validator, works on the create body. The update body holds only the fields that the client sends, and the other fields are None. Check such a rule in update, where you have the stored row too.

Check what the schema cannot see#

A schema sees one request. It does not see other rows, the stored row or the caller:

  • A reference to another row: fr.MustExist, fr.IDRef and fr.IDSchema[Model] check that the row exists, and return 404 if it does not. See Relationships.

  • A unique value, such as an email address: put a unique constraint on the column. The database rejects a second row with the same value, and Restly turns the error into a 409; see Errors.

  • A rule that needs the database or the caller, such as “no new tasks in an archived project”: check it in the create or update business method and raise an error there; see Request Lifecycle & Hooks. The SaaS example checks such rules in app/tasks/views.py.

Use other field names in JSON#

Use a normal Pydantic alias when the JSON name differs from the Python name:

from pydantic import Field


class UserSchema(fr.IDSchema):
    first_name: str = Field(alias="firstName")
    email: str

A request body must use firstName. The responses use firstName too. The Python name stays first_name, and Restly writes the value to the model attribute with that name. List filters use the alias as well; see Filtering & Pagination.

Set your own response class#

By default, the response class is the view’s schema without its WriteOnly fields. Restly builds this class even when the schema has no WriteOnly fields, so OpenAPI always shows UserResponse.

When what goes out differs more from what comes in, set schema_response on the view. Everything that goes out follows it:

  • every single response, and each item of the list response;

  • the fields that the list filters and sort keys use, so a client can filter only on what it can see;

  • the relationships that the view loads.

The request bodies still follow schema_create and schema_update, which Restly derives from schema:

class AccountSchema(fr.IDSchema):
    name: str
    email: str
    team_id: int | None = None


class AccountResponse(fr.IDSchema):
    name: str
    team: TeamSchema | None = None


class AccountView(fr.AsyncRestView):
    prefix = "/accounts"
    model = Account
    schema = AccountSchema
    schema_response = AccountResponse

POST /accounts takes name, email and team_id. Every response shows id, name and the nested team, which the view loads. ?email=... is not a filter, because a client does not see email. Restly uses the class as you wrote it: it does not remove WriteOnly fields from it.

Name the class <Resource>Response, as in AccountResponse. Restly names the list response and the list params after it: AccountListResponse and AccountListParams. For type checkers, put the class in the second type parameter of the view, as in fr.AsyncRestView[Account, AccountResponse]; see Type Annotations.

To change how one object becomes a response, or to send another shape, see Responses.

The names of the generated classes#

A class that Restly generates is named <Resource><Role>. Resource is the class name of the view’s schema without a final Schema or Response. For the view’s schema UserSchema, the resource is User:

Role

Class

View attribute

response

UserResponse

schema_response

create body

UserCreate

schema_create

update body

UserUpdate

schema_update

list response

UserListResponse

none

list params

UserListParams

schema_list_params

A client sees these names in OpenAPI. It does not see the view’s schema, unless another schema nests it or a custom route names it. The list params are not a class in OpenAPI either: OpenAPI shows them as separate query parameters.

The list response has no view attribute, because it has nothing of its own to set. It is the envelope of the view’s pagination, filled with the response class. To change it, change one of those two; see Change the list envelope. A react-admin view has no list response class: its list route returns a plain JSON list.

A view without a schema gets a generated one. For a model named User it is UserSchema, so the names above stay the same. A schema with another name keeps its full name as the resource: UserRead gives UserReadCreate.

Name your schemas#

OpenAPI keeps all classes in one list, by name. It has no modules. A generated client uses these names as type names. So each class in your API needs its own name, even when Python keeps two classes apart in different modules.

Restly names the classes that it generates after the view’s schema; see the names of the generated classes. Follow these rules for the classes that you write:

  • Name the view’s schema after the resource that the client sees: UserSchema, or AdminUserSchema for an admin view of users. Two schemas named UserSchema in different modules clash.

  • Use the names UserResponse, UserCreate and UserUpdate only for a view’s response class and its create and update body, and set the class on the view:

    class TaskCreate(fr.BaseSchema):
    title: str


class TaskView(fr.AsyncRestView):
    prefix = "/tasks"
    model = Task
    schema = TaskSchema
    schema_create = TaskCreate

    A class for another purpose, such as the body of a bulk route, gets a name that says what it is: TaskBulkItem, UserSummary.

  • Two views that share a schema also share the names of the classes that Restly generates. When the classes differ, for example because only one view is paginated, give one view a schema of its own:

    class AllTasksSchema(TaskSchema):
    pass

    The list response takes its name from the response class. So when the two views set the same schema_response, give one view a response class of its own in the same way.

Two different classes can still get the same name. For example, two views share a schema but only one is paginated, or you wrote a UserCreate that is not the same as the generated one. OpenAPI then shows both classes under long names built from the module path, such as app__users__views__UserCreate. When the module path is the same too, it numbers them, and the numbers follow the order in which the views are registered. These names can change, and a generated client then breaks.

When the app builds its OpenAPI spec, Restly checks for this and warns with a RestlyDuplicateSchemaNameWarning that names the classes and the views. Restly checks an app that you pass to fr.configure(app, ...) or configure_tests(app=...), or that you include a view on. Two classes with the same name are not a problem when their JSON schemas are the same, docstrings and defaults included: OpenAPI then shows them as one.

Name the view’s classes in a custom route#

A custom route that returns a single object or a list can show the same types in OpenAPI as the CRUD routes. A route decorator runs in the class body, before Restly builds the response classes. So a custom route gets the classes from two functions, at module level. Each returns the same class that the view uses: derive_schema_response(schema) and derive_schema_list_response(schema_response, pagination=...). Pass the view’s pagination as it is, also when it is None:

UserResponse = fr.schemas.derive_schema_response(UserSchema)
UserListResponse = fr.schemas.derive_schema_list_response(
    UserResponse, pagination=AppView.pagination
)


@fr.include_view(app)
class UserView(AppView):
    prefix = "/users"
    model = User
    schema = UserSchema

    @fr.get("/inactive", response_model=UserListResponse)
    async def inactive(self, list_params):
        result = await self.handle_get_many(list_params, where=User.active.is_(False))
        return self.to_response(result, fr.ResponseShape.LIST)

    @fr.post("/{id}/activate", response_model=UserResponse, status_code=200)
    async def activate(self, id: int):
        user = await self.get_one(id)
        async with self.write_action("activate", obj=user):
            user.active = True
        return self.to_response(user)

OpenAPI then shows UserListResponse and UserResponse for these routes, as for the CRUD routes. The SaaS example names its classes this way in app/projects/views.py.

A view with its own schema_response passes that class to derive_schema_list_response instead.

A function builds these classes, so type checkers do not accept them in an annotation, as in data: UserResponse. mypy also does not accept them inside a type in other places, as in response_model=list[UserResponse]. At runtime they are normal classes, so add # type: ignore[valid-type] on such a line.

A custom route that names UserSchema or PaginatedEnvelope[UserSchema] sends the same JSON, but shows a type of its own in OpenAPI. A route that passes a pagination with another envelope than the view’s gets a list response of another shape, for example data without total_count. There are then two classes named UserListResponse, and Restly warns; see Name your schemas.

Validate the document in a JSON column#

A JSON column maps to a bare dict, which does not check the fields of the document. To check its shape, write the schema yourself and give the field a nested Pydantic model as its type. Restly calls model_dump(mode="json") before it assigns the document to the column. The view’s schema validates the stored document when it is read back.

A document with a WriteOnly or a Field(exclude=True) field raises RestlyConfigurationError before Restly assigns it. This includes such fields in nested models. The dump would leave those fields out, so they would not be stored. A document with dataclasses or iterators raises the same error. For such documents, use a SQLAlchemy TypeDecorator that defines how the document is stored. Its bind processor receives the Pydantic model itself, not a dump.

You can still mark the whole JSON column WriteOnly. That hides the column in responses, and the stored document keeps all its fields.

Internals#

This section explains how Restly builds the classes. You do not need it to use them.

How the markers work#

ReadOnly and WriteOnly are typing.Annotated aliases. Each one adds a marker object and a Pydantic Field to the type:

  • ReadOnly[T] is T with the read-only marker and a readOnly flag for the JSON schema.

  • WriteOnly[T] is T with the write-only marker, a writeOnly flag for the JSON schema, and exclude=True. Pydantic’s exclude removes the field in every serialization of the schema. A value can only leak through a response that never passes through the schema, such as a raw dict or ORM object that a route returns without a response_model.

Restly finds a marker in the field’s top-level metadata. That is why a marker inside a union or a container is rejected. BaseSchema checks this when the class is defined. A view checks its own classes again when it registers, which also covers classes that do not derive from BaseSchema.

How Restly builds the request bodies and the response class#

before_include_view() builds the classes. For the view’s schema UserSchema:

  • schema_response comes from derive_schema_response(). It is a subclass of UserSchema that deletes the WriteOnly fields. Each call with the same schema returns the same class, so a custom route can name it.

  • schema_create is a subclass of UserSchema with OmitReadOnlyMixin first in the MRO. That mixin deletes the ReadOnly fields from cls.model_fields and rebuilds the class with model_rebuild(force=True).

  • schema_update adds PatchMixin as well. After the ReadOnly fields are gone, it sets the default of every field to None and makes its type Optional[...]. The defaults of UserSchema are replaced by None, not kept. A field that the client does not send is not written: Restly writes only the fields in model_fields_set.

Both request bodies also leave out a primary key that the server generates, even when the schema does not mark it ReadOnly. Generated means an autoincrement column, a column with a default, or a dataclass field outside __init__. A primary key without any of these is a natural key, and the client sends it.

The classes are subclasses, so they keep the validators of UserSchema. The response class keeps the validator of a WriteOnly field that it deletes, and Pydantic does not run it there. The request bodies do not do this for the ReadOnly fields that they delete. So a validator for a ReadOnly field makes the view fail when it registers, unless the validator has check_fields=False.

Restly stores the classes on the view when it registers the view. Declare schema_response, schema_create or schema_update on the view class to use your own class instead.

When a subclass view gets new classes#

A subclass inherits the classes that its base view declares. Registration builds a class again for the subclass in two cases: Restly generated it for the parent, or what it is built from changes. A subclass that declares a new schema gets a new schema_response, schema_create, schema_update and schema_list_params. A subclass that declares a new schema_response gets new schema_list_params. A view without a schema builds it from model, so there a new model counts as a new schema. A class that Restly generates for the subclass is not a change of its own, so it does not replace a class that the base declares.

How Restly generates a schema#

derive_schema(model, ...) builds the schema of a view without one. It makes one field for each column on the model’s SQLAlchemy mapper, inherited columns included. A column’s type comes from its Mapped[T] annotation, or from the plain annotation on a SQLModel table. Under from __future__ import annotations, Restly evaluates the annotation string in the model’s module. When no annotation resolves, the column type’s python_type is used. A column with neither raises TypeError that names the attribute. Synonyms and composites get no field of their own: the columns behind them already have one. A column with a default, or a nullable column, gets an optional field.

Three rules decide the rest:

  • Base classes: Restly checks whether the model has fields named id, created_at and updated_at, and picks IDSchema, TimestampsSchemaMixin and BaseSchema from that. It does not look at the model’s Python base classes. A model with a field named id for another reason also gets IDSchema.

  • ReadOnly fields: the fields id, created_at and updated_at are always ReadOnly. So is a column_property over a SQL expression, which cannot be written. Any other column that the server fills, for example with a server default, is not ReadOnly.

  • Relationships: never included. A foreign key column, such as customer_id, is an ordinary field. To show a related row in a response, write the schema yourself, for example with an IDRef[Customer] field; see Relationships.

A view and a direct call of derive_schema(model) give the same schema.
