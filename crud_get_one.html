Get One#

GET /{id} returns one row of the view’s model. A read changes nothing, so it has no business method and no commit. How a CRUD route runs explains the methods of each route. For GET /{id}, these steps run:

  • GET /{id}
    • get_one_endpoint(id)overrideThe endpoint method.
      • handle_get_one(id)The handler. You call it, but you cannot override it.
        • get_one(id)The load. You call it, but you cannot override it.
          • select()The model, the scope and the loader options.
          • where_id(id)overrideThe WHERE that picks the row: the primary key by default.
          • not_found(id)overrideThe error when no row matches: a 404 by default.
        • authorize("get_one", obj=obj)overrideA refusal is a 403.
      • to_single_response(obj)overrideThe response.

A method marked override is a method that you can override in your view.

Visibility, then policy#

A read decides in two steps whether the client gets the row:

  • Visibility. The load starts from select(): the model with the view’s scope. A row outside the scope is a 404 for every caller, as if the row did not exist. See Scopes.

  • Policy. The handler calls authorize with the loaded row. A refusal is a 403. See Authorization.

PATCH /{id}, DELETE /{id} and your action routes load their row with the same get_one. So the scope, where_id and not_found apply to them too.

Details

You cannot override the loads: a view class that defines get_one, get_many or select fails when Python creates the class. The message names the place for each change. An override of a load could leave out the scope, or the scope= that a route asked for, and nothing would tell you. Because you cannot override the loads, the scope always applies.

select() also adds the options of get_loader_options, so the rows are ready for the response. A custom read starts from it too, as in self.select().where(Item.price > 10). In a count, a subquery or a select of some columns, SQLAlchemy leaves the loader options out.

Find the row by another key#

By default, the item routes find the row by its primary key. To find it by another column, such as a slug, override where_id. It gets the id from the path and returns the WHERE that picks the row. Set id_type to the type of the value in the path:

from sqlalchemy import ColumnElement


@fr.include_view(app)
class RecipeView(fr.AsyncRestView):
    prefix = "/recipes"
    model = Recipe
    schema = RecipeSchema
    id_type = str

    def where_id(self, id: str) -> ColumnElement[bool]:
        return Recipe.slug == id

Now GET, PATCH and DELETE /recipes/{slug} find the recipe by its slug, and so does self.get_one(slug) in your own routes. To change the error for a row that does not exist, override not_found. It returns the exception that get_one raises:

    def not_found(self, id: str | None) -> Exception:
        return fr.exc.NotFound(f"No recipe has the slug {id!r}")

To find a row by another key in one route only, pass an expression to the handler; see Read a row by another key.

Details

where_id is a plain def, also on an async view: it builds SQL and runs no query. not_found may be async def on an async view, and Restly awaits it. When a route loads by an expression, not_found gets None, because the 404 body is no place for SQL. A hook that returns the wrong kind of value raises TypeError.

Combine columns with sqlalchemy.and_(...). This is how a route reaches a row of a model with a composite primary key. A plain id cannot name such a row, so a view of such a model must override where_id to read the parts from the path, such as "3-7". Set id_type = str too: without it, the path takes only an integer, and /seats/3-7 is a 404 before where_id runs. Then the default item routes work for the model:

class SeatView(fr.AsyncRestView):
    prefix = "/seats"
    model = Seat
    id_type = str  # the id in the path is "3-7"

    def where_id(self, id: str) -> ColumnElement[bool]:
        row, _, number = id.partition("-")
        if not (row.isdigit() and number.isdigit()):
            raise self.not_found(id)
        return sqlalchemy.and_(Seat.row == int(row), Seat.number == int(number))

A view that keeps the default where_id fails when it registers, unless it leaves the item routes out: get_one_endpoint = None, update_endpoint = None and delete_endpoint = None.

The WHERE narrows the read inside the scope. It never reaches past it, so a row that the view hides stays a 404 under any key. Only scope changes what the view sees. When more than one row matches, Restly raises SQLAlchemy’s MultipleResultsFound and does not return the first row: a key that matches several rows is a bug in the expression.

The expression that where_id returns compares columns of the view’s model. A column of another table raises TypeError, because SQL would join every row of that table and could pick a wrong row. For a condition on a related row, use .has() or .any(), such as Book.shelf.has(Shelf.code == code).

Replace get_one_endpoint#

To change one option of the route, such as its dependencies, use fr.modify_route. When the change needs code, define get_one_endpoint in your view, with a route decorator. Keep the call to handle_get_one, so the scope and authorize still run. This view lets clients keep the row for a minute:

from fastapi import Response
from fastapi_restly.views import IDType, ViewResponse


@fr.include_view(app)
class ProductView(fr.AsyncRestView):
    prefix = "/products"
    model = Product

    @fr.get("/{id}")
    async def get_one_endpoint(self, id: IDType, response: Response) -> ViewResponse:
        response.headers["Cache-Control"] = "max-age=60"
        return await self.handle_get_one(id)

response: Response is FastAPI’s way to set a header on the response; see Response Headers. IDType and ViewResponse stand for the id type and the response schema of the view; see Name the view’s schemas in a custom route. Replace an endpoint method has the rules for all five routes.

A read that does not come from the database, such as one from a cache or another service, replaces the endpoint method in the same way. It does not call handle_get_one, so it calls authorize itself.

Read a row from a custom route#

handle_get_one runs all the steps of GET /{id}. Call it from a route of your own to read a row under another path. It takes the id of the row, or a SQLAlchemy expression that picks the row:

    @fr.get("/me")
    async def get_me(self) -> ViewResponse:
        return await self.handle_get_one(Current.user_id())

Current.user_id() is the id of the caller; see Request Context. The scope and authorize run as on GET /users/{id}. The route /me works beside /{id}, because Restly adds the routes of the view before the CRUD routes. Add a custom read route has more examples, such as a read that starts from self.select().
